# Схема базы данных

Готовый скрипт находится в [`schema.sql`](./schema.sql). Он рассчитан на PostgreSQL 14+ и запускается, например, так:

```bash
psql "$DATABASE_URL" -f db/schema.sql
```

Скрипт создает расширения `pgcrypto` (UUID и `gen_random_uuid()`) и `pg_trgm` (быстрый поиск по части имени/локации), все внешние ключи, ограничения целостности и индексы для ленты.

## Связи таблиц

```text
users 1 ──── * posts 1 ──── * post_media
  │             │
  │             ├──────────── * likes * ──── 1 users
  │             └──────────── * comments
  │                                  └────── parent_id (ответ на комментарий)
  │
  ├──────────── * follows (follower_id)
  ├──────────── * follows (following_id)
  ├──────────── * stories 1 ──── * story_views * ──── 1 users
  ├──────────── * messages (sender_id)
  ├──────────── * messages (receiver_id)
  └──────────── * notifications (user_id / actor_id)
```

- `users` — учетная запись и профиль. Уникальность `username` и `email` нечувствительна к регистру: `Alice` и `alice` не могут быть двумя аккаунтами. `email_verified_at` оставлен для статуса подтверждения email; `updated_at` используется при редактировании профиля.
- `follows` — связь подписки. Одна пара пользователей может иметь только одну запись. Для публичного аккаунта используется `accepted`, для приватного — сначала `pending`, а после одобрения — `accepted`. Самоподписка запрещена.
- `posts` — публикация пользователя. При удалении пользователя его посты удаляются каскадно.
- `post_media` — медиа поста, поэтому карусель хранится отдельными строками. `order_index` начинается с `0` и уникален внутри поста; `media_type` ограничен `image`/`video`.
- `likes` — лайк поста. Уникальное ограничение `(user_id, post_id)` не позволяет поставить один и тот же лайк дважды.
- `comments` — комментарии и ответы. `parent_id IS NULL` означает корневой комментарий, иначе запись является ответом. При удалении поста удаляется дерево его комментариев.
- `stories` — фото/видео с `expires_at`; по умолчанию срок жизни составляет 24 часа. Историю нужно выбирать с условием `expires_at > now()` — удалять просроченные строки физически необязательно.
- `story_views` — просмотры историй. Уникальная пара `(story_id, user_id)` хранит один просмотр каждого зрителя.
- `messages` — личные сообщения между `sender_id` и `receiver_id`, включая текстовое или медиа-сообщение. `is_read` позволяет быстро выбрать непрочитанные сообщения.
- `notifications` — уведомление для `user_id`, созданное пользователем `actor_id`. `entity_id` — ID связанной сущности (поста, комментария или подписки); он оставлен полиморфным, потому что тип сущности зависит от `type`.

Внешние ключи с `ON DELETE CASCADE` удаляют зависимые данные вместе с владельцем (например, лайки вместе с постом). Для `notifications.actor_id` используется `ON DELETE SET NULL`, чтобы история уведомлений не исчезала, если аккаунт автора удален.

## Почему нужны индексы

- `posts (user_id, created_at DESC, id DESC)` — основной путь для хронологической ленты подписок; `id` дает стабильную сортировку при одинаковом времени.
- Индексы на обеих сторонах `follows` позволяют быстро получить подписки пользователя и его подписчиков.
- `post_media (post_id, order_index)` и индексы комментариев ускоряют загрузку каруселей и дерева ответов.
- Индексы лайков, просмотров историй и уведомлений ускоряют счетчики, списки и выборку непрочитанных элементов.
- `posts` имеет полнотекстовый индекс по `caption`, а `users.username`, `users.full_name` и `posts.location` — trigram-индексы для поиска по `ILIKE '%строка%'`.

## Важные правила на уровне API/транзакций

- При создании поста API должен добавить хотя бы одну строку в `post_media` в той же транзакции. Одним обычным `CHECK` это правило между таблицами не выразить.
- Для ответа на комментарий API должен проверить, что `parent_id` принадлежит тому же `post_id`; внешний ключ гарантирует существование родителя, но не совпадение поста.
- Для приватного профиля создание `follows.status = 'pending'` и проверка одобрения должны выполняться в одной транзакции с бизнес-операцией.
- Истечение story определяется запросом к `expires_at`; фоновой очистке можно добавить `DELETE ... WHERE expires_at <= now()` позже.

Эта итерация содержит только SQL-схему, индексы и ограничения из пункта 1. API, JWT/refresh-token хранилище, WebSocket-чаты и UI будут отдельными этапами.
